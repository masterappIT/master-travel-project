# 內置客服需求記錄

記錄日期：2026-10-10（Asia/Shanghai）
狀態：需求已記錄；乘客端與管理後台已有介面草稿，訊息、語音、通話及獨立客服登入尚未接入。

## 使用者已確認的要求

1. 建立專案內置客服，不接第三方客服 API。使用者確認舊第三方客服整合從未使用，可直接移除，不需將其舊對話遷移列入方案。
2. 客服人員可透過獨立入口登入並處理對話，不依賴管理後台登入；已獲授權的管理後台人員也可以在管理後台操作同一套客服功能。兩個入口都須能查看、回覆及按既有乘客／司機 ID 主動聯繫，具體角色權限待定。
3. 未登入乘客也可以使用客服，保留訪客客服能力。
4. 客服人員需要能使用專案現有的乘客 ID 或司機 ID，直接找到對應的現有帳戶並主動聯繫；不能要求先建立第三方客服帳戶或改用另一套身份 ID。
5. 內置客服同時需要語音訊息與即時語音通話。兩者都屬已確認範圍；各端使用權限、通話錄製及保留政策仍待決定。
6. 先完成乘客端與管理後台介面，再依後續授權接入資料、API、身份驗證及跨端語音能力。
7. 乘客與客服對話須支援上傳圖片及影片；從訂單詳情、候車或行程進行頁聯繫客服時，介面應帶出該訂單／行程的識別及狀態。此輪僅完成 UI，實際媒體上傳、訊息傳送與訂單關聯後續接線。

- 乘客端已顯示圖片／影片附件入口，並可由現有訂單／行程頁帶出訂單 ID 與狀態供畫面參考；附件按鈕維持停用。畫面資訊不等於後端已建立客服對話，也不可作為訂單讀取授權。
- 目前沒有可用的客服對話 API 或獨立客服登入入口；[管理後台消息推送頁](../admin/src/pages/notifications/NotificationsPage.js) 屬於另一項功能。

## 整合建議（方案，尚非已批准的實作設計）

### 身份、工作入口與對話

- 建議提供獨立的客服工作介面與登入流程，以及後端專屬的客服人員身份、權限和 session；同時在管理後台提供客服操作頁。獨立入口不以管理員 session 作為登入條件，管理後台入口沿用其現有登入並由後端另行檢查客服操作權限。兩個入口共用後端客服對話、訊息與通話資料及同一套業務規則，分別保留操作者身份與稽核紀錄；介面路由、部署位置、帳戶管理和管理員角色權限在實作前定案。
- 對話參與者使用明確的 `PASSENGER`、`DRIVER`、`GUEST` 類型。已登入乘客和司機分別引用現有 `User.id`、`Driver.id`，由後端依其現有 session 確認對話歸屬；客服主動聯繫時，後端先按類型查找真實帳戶，再建立或開啟對話，記錄操作人與時間。不能把前端送來的 ID 當作讀取或寫入授權。
- 訪客保留獨立對話能力。現有乘客端以本機 `support-rider-id` 字串辨識訪客；建議改由後端核發不可任意猜測或冒用的訪客憑證，並規劃裝置遺失或清除資料後的處理。訪客不會自動對應成既有乘客 ID。
- 對話應具備訊息排序與去重、未讀狀態、客服指派、關閉／重開及操作稽核；第一版的具體工作流程和通知規則待產品決策。司機端目前只有靜態「聯繫客服」頁，直接聯繫司機要包含司機接收、回覆及未讀提示的設計與驗收。

### 文字、語音訊息與即時通話

- 建議用同一對話識別串起文字、圖片、影片、語音訊息和通話事件；訊息內容、發送者、收件對象、狀態與時間戳保存在 PostgreSQL。圖片、影片與語音檔案放私有媒體儲存，透過短效授權存取，明確限制格式、大小、時長、保留期限與刪除流程；不要將媒體二進位直接塞進對話資料表。專案現有私有 Cloud Storage 用於分享圖片，客服媒體的儲存範圍與存取政策需另外設計。
- 訂單／行程入口可在畫面傳入既有訂單 ID 與狀態作為聯繫情境；正式接線時，後端須按乘客或訪客身份重新核對訂單存取權與即時狀態，不能信任前端 query。訪客能否就既有訂單聯繫客服也須以授權規則明確界定。
- 即時通話建議先做跨平台可行性驗證，再選定自管 WebRTC 架構。其服務包含信令、呼叫狀態與超時、ICE/STUN/TURN、權限提示、斷線重連及多裝置處理。信令可評估接入既有 API 或獨立服務；TURN 需要適合其網路協定的獨立部署與維運。此方案不接第三方客服或通話 API，但基礎設施仍可沿用專案既有雲服務。
- 乘客端有 H5、微信小程序與 App Plus，司機端為 Flutter Web。語音錄製及即時通話不能以單一平台成功推定全平台可用；先在每個目標平台驗證麥克風權限、錄製、播放、前後台、接聽及網路切換。尤其小程序通話能力、平台審核／配置及 App Plus 行為，要以實機原型結果決定介面與通話技術。即時通話錄製不是已確認需求，不應預設儲存通話音訊。
- 正式 API 使用 Cloud Run。若信令使用 WebSocket，需設計連線逾時後重連、跨實例狀態同步及部署網路；不能把持久連線或 TURN 直接當作現有 HTTP API 的自然延伸。

### 建議交付順序與驗收門檻

| 階段 | 最小交付範圍 | 進入下一階段前的驗收 |
|---|---|---|
| 0. 決策與原型 | 確認各身份能否發起／接聽、客服排班與指派、通知及留存政策；驗證 H5、小程序、App Plus、Flutter Web 的語音訊息與即時通話可行性 | 各平台實機或目標瀏覽器的錄製／播放／通話證據、網路與部署方案、失敗路徑 |
| 1. 內置文字客服 | 客服獨立登入與工作介面、管理後台客服操作頁、乘客／司機／訪客對話、按既有 ID 主動聯繫、收發文字及權限稽核 | 兩個工作入口操作同一對話且權限、操作者紀錄正確；客服與獲授權管理員能主動聯繫既有乘客及司機，兩端能接收和回覆；訪客流程可用 |
| 2. 語音訊息 | 錄製、上傳、播放、權限、私有媒體與清理 | 支援範圍內各端完成收發；檔案不可跨對話存取；重試、取消及過期行為可驗證 |
| 3. 即時語音通話 | 自管信令與通話服務、呼叫／接聽／拒絕／結束、超時及斷線處理 | 目標平台雙向音訊與背景／網路切換測試；TURN 故障、無人接聽及重連有明確結果 |
| 4. 啟用與驗收 | 啟用新入口；不安排未使用的舊對話遷移 | 全端回歸、正式配置／監控／回滾方案與實際發布驗收 |

## 後續實作前須核對

若之後授權實作，須按專案規範重新核對當時工作樹、適用指令與技能，確定乘客端、司機端、客服獨立工作介面、管理後台客服頁、API、資料庫及部署文件的修改邊界。乘客與司機的 ID 必須由後端對應現有帳戶，不可僅憑前端提交的 ID 授權讀取對話；登入用戶的對話歸屬應由後端驗證現有登入 session，訪客對話需有不能任意冒用的身份憑證。獨立客服入口與管理後台入口都需要明確的客服操作權限與稽核邊界。跨端完成狀態需以實際功能與平台驗證結果為準。
