# 內置客服需求記錄

記錄日期：2026-10-10（Asia/Shanghai）
狀態：第一版文字客服已在程式碼接入乘客、司機、訪客、管理後台及獨立客服入口；本機 API 流程已測，仍待目標平台互動驗收與正式部署。圖片目前只有管理端媒體基礎，尚未成為客服訊息。影片、語音訊息與語音通話不在目前範圍。

## 使用者已確認的要求

1. 建立專案內置客服，不接第三方客服 API。使用者確認舊第三方客服整合從未使用，可直接移除，不需將其舊對話遷移列入方案。
2. 客服人員可透過獨立入口登入並處理對話，不依賴管理後台登入；已獲授權的管理後台人員也可以在管理後台操作同一套客服功能。第一版由 `SUPER_ADMIN` 建立專屬客服帳戶，`SUPER_ADMIN`／`OPERATOR` 可在管理後台查看、回覆及按既有乘客／司機 ID 主動聯繫。
3. 未登入乘客也可以使用客服，保留訪客客服能力。
4. 客服人員需要能使用專案現有的乘客 ID 或司機 ID，直接找到對應的現有帳戶並主動聯繫；不能要求先建立第三方客服帳戶或改用另一套身份 ID。
5. 客服目前只需要文字與圖片訊息；影片、語音訊息與即時語音通話不列入目前功能範圍，也不保留相關設定或 UI 入口。
6. 第一版採共用收件匣，暫不做指派、關閉與通知；先接入文字，圖片訊息留待後續階段。
7. 乘客與客服對話須支援上傳圖片；從訂單詳情、候車或行程進行頁聯繫客服時，介面應帶出該訂單／行程的識別及狀態。訂單情境目前只在畫面呈現，尚未由後端驗證與保存。

## 目前實作參考

- [乘客端聊天頁](../src/pages/support/chat.vue)、[司機端客服頁](../driver/lib/contact_support_page.dart)、[管理後台客服頁](../admin/src/pages/support/SupportPage.js)與[獨立客服工作台](../admin/support-agent.html)已接入同一套文字對話 API。介面以定時讀取取得新訊息。兩個工作入口的收件匣顯示對象姓名與電話並可依此搜尋，訊息顯示回覆者名稱，可載入更早訊息及多行回覆；停留在客服頁面時，新訊息會以分頁標題待回覆數、畫面提示與可關閉的提示音提醒（非系統推播，離開頁面後不提醒）。獨立客服工作台以手機 Web 為主要使用場景，採聊天版面：手機一次只顯示對話列表或單一對話（輸入列固定在底部），寬螢幕並排；主動聯繫改由「新對話」彈出面板進行。列表可按乘客／司機／訪客分類並顯示各類待回覆數，對話標示身份，可直接撥打對象電話，司機另顯示在線狀態；客服可自行修改密碼。後台客服頁維持桌面管理版面（左側對話列表、右側對話），頁首只留標題、服務狀態、「新對話」與「設定」；功能開關收在「設定」內，主動聯繫同樣改為彈出視窗。兩個入口維持兩套各自的介面。
- 乘客、司機沿用各自現有 session；訪客使用後端核發的隨機憑證，憑證遺失後無法恢復舊訪客對話。客服可用現有 `User.id`／`Driver.id` 建立或開啟對話。訊息有排序、去重及操作者稽核。
- 管理員權限為 `SUPER_ADMIN`／`OPERATOR`，獨立客服帳戶由 `SUPER_ADMIN` 在管理後台的管理員帳戶頁建立、改名、重設密碼、解鎖、強制登出及啟停；兩個工作入口共用收件匣。圖片附件按鈕仍停用；正式環境的圖片媒體端點暫停使用，避免 Cloud Run 暫存檔案遺失，待持久化私有儲存接入後才開放。`SupportMedia` metadata 與管理端圖片媒體端點尚未關聯實際訊息或開放給對話參與者。
- [管理後台消息推送頁](../admin/src/pages/notifications/NotificationsPage.js)是另一項功能。訂單／行程資訊只供畫面參考，不能作為訂單讀取授權。

以上是目前程式碼狀態；正式啟用仍須完成目標平台驗收、部署配置及圖片訊息階段。

## 實作邊界與後續工作

### 身份、工作入口與對話

- 獨立客服工作介面使用後端專屬帳戶、session 與 CSRF；管理後台沿用管理員 session，兩個入口共用後端對話與訊息資料，分別記錄操作者身份與稽核紀錄。
- 對話參與者使用明確的 `PASSENGER`、`DRIVER`、`GUEST` 類型。已登入乘客和司機分別引用現有 `User.id`、`Driver.id`，由後端依其現有 session 確認對話歸屬；客服主動聯繫時，後端先按類型查找真實帳戶，再建立或開啟對話，記錄操作人與時間。不能把前端送來的 ID 當作讀取或寫入授權。
- 訪客使用後端核發的不可猜測憑證，儲存在乘客端本機；不會自動對應既有乘客 ID。
- 第一版有訊息排序、去重及稽核；共用收件匣沒有逐則已讀狀態、指派、關閉／重開或通知。後台儀表盤會以最近客服回覆推算待回覆的乘客、司機或訪客消息數，點擊後進入共用收件匣。司機端可開啟對話及回覆，仍須目標瀏覽器互動驗收。

### 文字與圖片訊息

- 建議用同一對話識別串起文字與圖片訊息；訊息內容、發送者、收件對象、狀態與時間戳保存在 PostgreSQL。現階段已落地圖片 metadata、格式驗證、10 MB 輸入上限、EXIF 方向校正、display／thumbnail WebP 壓縮、checksum、私有管理端讀取與刪除；本機開發二進位使用 `SUPPORT_MEDIA_STORAGE_DIR` 私有目錄，原始檔不保存。正式 Cloud Run 仍需接入私有 Cloud Storage adapter、短效 signed URL、保留期限清理及對話參與者授權；不要將媒體二進位直接塞進對話資料表。專案現有私有 Cloud Storage 用於分享圖片，客服媒體的儲存範圍與存取政策仍需另外配置。
- 訂單／行程入口可在畫面傳入既有訂單 ID 與狀態作為聯繫情境；正式接線時，後端須按乘客或訪客身份重新核對訂單存取權與即時狀態，不能信任前端 query。訪客能否就既有訂單聯繫客服也須以授權規則明確界定。
- 正式 API 使用 Cloud Run。圖片上傳仍需完善對話參與者權限、私有媒體存取、失敗重試及清理；不可把前端停用狀態當成後端授權。

### 建議交付順序與驗收門檻

| 階段 | 最小交付範圍 | 進入下一階段前的驗收 |
|---|---|---|
| 0. 決策與原型 | 確認各身份能否發起／回覆、客服排班與指派、通知及留存政策；驗證圖片上傳與文字訊息的跨端可行性 | 各平台實機或目標瀏覽器的文字／圖片收發證據、權限與失敗路徑 |
| 1. 內置文字客服 | 客服獨立登入與工作介面、管理後台客服操作頁、乘客／司機／訪客對話、按既有 ID 主動聯繫、收發文字及權限稽核 | 兩個工作入口操作同一對話且權限、操作者紀錄正確；客服與獲授權管理員能主動聯繫既有乘客及司機，兩端能接收和回覆；訪客流程可用 |
| 2. 圖片訊息 | 圖片選取、上傳、預覽、權限、私有媒體與清理 | 支援範圍內各端完成收發；檔案不可跨對話存取；重試、取消及過期行為可驗證 |
| 3. 啟用與驗收 | 啟用新入口；不安排未使用的舊對話遷移 | 全端回歸、正式配置／監控／回滾方案與實際發布驗收 |

後續按變更範圍執行 `README.md` 與 `docs/DEVELOPMENT.md` 的 scope、依賴及各端驗證門檻。建置結果不能取代跨平台功能與互動驗收。

## 後續實作前須核對

後續階段須按專案規範核對工作樹、適用指令與技能。圖片讀取與訊息關聯須按對話參與者和工作人員身份授權；訂單情境須由後端重新驗證。跨端完成狀態以實際功能與平台驗證結果為準。
